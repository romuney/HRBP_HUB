# HRBP HUB v2 — что куда вставлять

Отчёт целиком — **один ноут Helicopter, семь таблиц ClickHouse, один датасет и
один чарт** в Proteus. Всё, что в макете было полкой фильтров, шапкой, вкладками и
окном KPI, живёт в этом чарте. Как устроено — `docs/architecture.md` в репозитории.

| Файл | Куда вставлять |
|---|---|
| `1. Helicopter — ноут HRBP HUB.yaml` | Helicopter → ноут «HRBP HUB» → импорт YAML (20 параграфов) |
| `2. Proteus — датасет hrbp_hub.sql` | Proteus → виртуальный датасет **hrbp_hub**, база CROSS → SQL |
| `3. Proteus — чарт HRBP HUB.js` | чарт «HRBP HUB» (тип ECHARTS) → JS |
| `4. CSS борда (дописать в конец).css` | Edit dashboard → CSS, в конец; `000000` → id чарта (необязательно) |
| `5. SQL Lab — проверки после выгрузки.sql` | SQL Lab, база CROSS: проверить выгрузку до заведения датасета |

## Что нового в v2

- **Оргструктура — уровни 1 и 3…12, как в ультраширокой витрине.** `lvl2`
  пропускается (блоки 3-го уровня — дети компании), глубже 12-го — обрезается:
  сотрудники 13-го уровня считаются в своём юните 12-го.
- **«Команды» — дерево до 12-го уровня.** −1 и −2 приезжают сразу, глубже —
  подгружаются при раскрытии (секунда-две, строка «Загружаю подразделения…»).
- **Масштаб ≈100 тыс. сотрудников.** Новая седьмая таблица `hrbp_hub_base` —
  база сравнения «вся компания» без пути; запрос читает только ветку выбранного
  юнита. Для зоны больше 1 500 юнитов (супер-HRBP, админ) выбор юнита показывает
  путь и окрестность, а поиск по Enter ищет по всей зоне.
- **Вид — как у отчёта Proteus Adoption:** те же шрифт, кегли и веса (без жирного 700),
  размеры значков и кареток, контролы высотой 34 px, отступы панелей, карточек и таблиц.
- «Трансформеры», «Цели» и «Каталог» — без изменений по смыслу.

**Если v1 уже вставлен** — замените файлы 1–3, остальное не трогайте:

1. **Сохраните свои правки ноута** до импорта: строки INSERT из «KPI · реестр целей»,
   значения в «HH · параметры» (`super_hrbp_unit_rk`, админы, `active_type_value`),
   `OWNERS` в «Доступ к таблицам в Proteus». В файле 1 эти параграфы в исходном
   виде — после импорта верните правки на место.
2. Запустите ноут целиком: появится `prod_proteus.hrbp_hub_base`, в справочнике —
   колонки `kids_n` и `sub_n`.
3. SQL Lab, файл 5: проверки 1 (семь таблиц), 4 (база = куб) и 6 (уровни).
4. Датасет `hrbp_hub`: SQL — файл 2 целиком, сохранить. Колонки те же 29 —
   «Синхронизировать столбцы» не обязательно, но и не вредит.
5. Чарт: JS — файл 3 целиком, сохранить. «Измерения», лимит строк и кросс-фильтры
   не меняются. CSS (файл 4) — тот же.

Первая установка — разделы 1–4 по порядку.

## 1. Ноут в Helicopter

1. Создайте ноут «HRBP HUB» и импортируйте файл 1. Параграфы идут по порядку;
   «Обновить кеш борда» и «Диагностика источников» выключены — так и должно быть.
2. Параграф **«HH · параметры»** — проверьте три вещи:
   - `super_hrbp_unit_rk` — юнит «лид эйчар» (как в ноуте «Связи и подчинения»);
   - `hh_param_admin` — логины админов отчёта (видят всю компанию), сейчас `r.kazantsev`;
   - `active_type_value` — точное значение `active_type_nm` для «Активной» численности.
3. Параграф **«KPI · реестр целей»** — пока пустой (есть закомментированный пример).
   Цели можно добавить позже, см. раздел 5.
4. Параграф **«Доступ к таблицам в Proteus»** — впишите логины команды отчёта в `OWNERS`.
5. Расписание — ежедневно после обновления `prod_v_emart.mdm_employee_structure_d`
   (первый параграф ждёт все четыре источника).
6. Запустите ноут целиком. Параграф **«HH · проверки»** падает делением на ноль, если
   что-то не так (дубли, длина массивов, численность куба ≠ источнику, база ≠ кубу,
   путь глубже 12-го уровня, пустой доступ) — до выгрузки в ClickHouse. Последние два
   запроса там — диагностика: сколько увольнений без regrettable-разметки и без
   причины, какие цели отсеяны.
7. Один раз руками запустите выключенный **«Диагностика источников»** и посмотрите
   значения разрезов и покрытие разметки — это ответы на открытые вопросы
   `business-context.md` и `filter-fields.md`.

## 2. Проверка выгрузки (SQL Lab)

Файл 5, запросы по одному. Главное: 1 — все семь таблиц на месте; 3 — численность
компании по месяцам совпадает с HR-отчётностью; 4 — база сравнения сходится с кубом;
5 — у всех 11 атрибутов одна и та же численность; 6 — уровни 1 и 3…12, как в
ультраширокой; 7 — впишите свой логин и логин знакомого HRBP: зона та, что ожидаете,
и видно, сколько в ней юнитов.

## 3. Датасет hrbp_hub

1. Proteus → Datasets → новый виртуальный датасет, база **CROSS**, имя `hrbp_hub`.
2. SQL — файл 2 целиком. Сохранение исполняет запрос (с пустыми фильтрами и вашим
   логином) — должно пройти за секунды.
3. Колонок 29: `role, id, pid, n, j`, 12 × `m_*`, 12 × `w_*`. Если меняли SQL у уже
   существующего датасета и колонки изменились — **«Синхронизировать столбцы»**,
   иначе чарт падает с 500 (в v2 колонки те же, что в v1).

## 4. Чарт и дашборд

1. Новый чарт на датасете `hrbp_hub`, тип **ECHARTS**, имя «HRBP HUB».
2. **Измерения** — все 29 колонок, точными именами (список — `proteus/FIELDS.md`).
   Мер нет. Сортировки нет. **Лимит строк — 10 000.** Серверная пагинация — выкл.
3. JS — файл 3 целиком. Сохранить.
4. Дашборд «HRBP HUB»: чарт во всю ширину, высота — сколько не жалко (1 100–1 400 px);
   внутри чарт прокручивается сам.
5. **Кросс-фильтры: чарт должен фильтровать САМ СЕБЯ.** Edit dashboard → настройка
   области кросс-фильтров → у чарта «HRBP HUB» в получателях его собственного фильтра
   должен стоять он сам (не в исключениях). Без этого выбор юнита, разрезов, оси
   трансформеров, раскрытие «Команд» глубже −2 и поиск по зоне не применяются —
   через 9 секунд чарт сам скажет об этом жёлтой плашкой.
   Нативные фильтры дашборда не нужны: все фильтры — внутри чарта.
6. CSS (файл 4, необязательно): убирает заголовок чарта и поля вокруг — замените
   `000000` на id чарта во всех местах.
7. Доступ к дашборду выдайте HRBP как обычно: что каждый видит, решает не Proteus,
   а таблица доступа внутри датасета (своя зона; супер-HRBP и админы — вся компания).
8. Когда борд опубликован — в ноуте включите «Обновить кеш борда», подставив slug.

## 5. Цели (KPI)

Цели живут в параграфе «KPI · реестр целей»: одна строка INSERT = одна цель.
Строку не нужно писать руками: в отчёте откройте нужный юнит → вкладка **«Цели»** →
блок «Новая цель»: метрика, значение, дата начала, комментарий → «Скопировать».
Разрезы цели берутся из строки фильтров (одно значение разреза — в правило,
мультивыбор — «все»). Строку вставьте в INSERT параграфа и перезапустите ноут.
Снять цель — удалить строку или закрыть её датой `valid_to`.

Как цель работает: действует на юнит и всю ветку вниз, пока ниже не встретится своя;
правило с разрезом видно, только когда в фильтрах выбран ровно этот разрез
(в реестре — статус «ждёт разреза», кнопка «Показать» выставит юнит и разрезы сама).
Целей нет у «Численности» и «Non regrettable текучести»: у них «больше» не значит «лучше».

## 6. Если что-то не так

| Симптом | Причина и что сделать |
|---|---|
| Жёлтая плашка «Фильтр не применился…» | нет самовлияния кросс-фильтра — п. 4.5 |
| «В данных чарта нет колонок: …» | не все 29 полей в «Измерениях» или не синхронизированы столбцы — п. 3.3, 4.2 |
| «Для вашего логина нет зоны HRBP» | логина нет в `hrbp_hub_access` — проверка 7 файла 5; админа добавить в «HH · параметры» |
| «Запрошенный юнит вне вашей зоны» | ссылка/фильтр с чужим юнитом — отчёт открыл вашу зону |
| «Нет служебной строки meta» | лимит строк слишком мал — п. 4.2 |
| «Подразделения не загрузились» в «Командах» | раскрытие глубже −2 не дошло до датасета — п. 4.5; свернуть и раскрыть ещё раз |
| В выборе юнита «N подразделений — откройте юнит» | зона больше 1 500 юнитов: дети подгружаются, когда юнит выбран; или поиск по Enter |
| Юнита 13-го уровня нет в отчёте | так и задумано: уровни — до 12-го, его люди — в юните 12-го уровня |
| Пустые месяцы в конце года | так и задумано: незакрытые месяцы не показываются |
| Ноут упал на «HH · проверки» | имя упавшей проверки = что сломалось; до ClickHouse битые данные не доехали |
| Цифры не сходятся с HR-отчётностью | проверки 3–4 файла 5 и параграф «Диагностика источников» |

## 7. Что проверено до поставки

- Все GP-параграфы исполнены на синтетике в PostgreSQL 16 (в источнике есть `lvl2`
  и `lvl13` — отчёт их пропускает); стоп-проверки зелёные.
- Датасет сверен число в число с независимым расчётом на ClickHouse 24.8 (как в бою)
  и 26.9: 173 и 171 проверка, 0 провалов (разные HRBP, юниты, разрезы, доступ,
  раскрытие до 12-го уровня, справочник большой зоны и поиск, враждебный ввод,
  сохранение датасета).
- Нагрузка на ClickHouse 24.8: ≈100 тыс. сотрудников, ≈10 тыс. юнитов, куб 37 и
  60 тыс. строк — ответ 1,1–1,7 с (компания, блок, раскрытия, поиск, разрезы, HRBP
  своей зоны), 50–380 КБ.
- Чарт: проверки скилла proteus-echarts-builder (статика + браузер, 0 FAIL) и живой
  стенд с настоящими кросс-фильтрами: все вкладки, выбор юнита 12-го уровня, раскрытие
  «Команд» вглубь, поиск по большой зоне, разрезы, оси, цели.
- Чего стенд не заменяет: боевые значения разрезов, `super_hrbp_unit_rk`, покрытие
  regrettable-разметки и настройки кластера Proteus — их показывают п. 1.7 и файл 5.
