### 08.10, восемнадцатая поставка — **«Применить» быстрее в разы** (файлы 2 и 3, порядок любой)

**Почему было 20 с.** Почти всё это время Proteus разбирал **текст** нашего SQL, а сам ClickHouse (по
замеру на стенде) считал 2–3 с. Proteus — это Superset 2: до запуска он прогоняет SQL датасета через
библиотеку sqlparse — «красиво форматирует» обёртку `SELECT … FROM (датасет) LIMIT 50000` (reindent) и
разбирает текст на ключ кеша. Форматирование растёт квадратично от длины SQL: у прежних 34 КБ это
9–11 с. А после правки
кеша (семнадцатая поставка) ключ кеша с логином считается на каждом шаге — на «Применить» (POST), в
фоновой задаче (дважды) и на каждом заборе результата `qc-…` — и каждый раз ≈2 с разбора. Отсюда и
«оптимизация пошла не туда»: правка безопасности умножила цену длинного SQL. Наш замер шагов
Superset на стенде (та же версия sqlparse): 18,6–20,5 с разбора на одно «Применить» плюс 2 с
ClickHouse — как у вас.

**Что сделано.** SQL датасета переписан втрое короче (34 → 13 КБ, 16 → 5,6 тыс. токенов разбора):
12 компонентов метрик едут через запрос одним массивом и режутся на 24 колонки один раз в самом верху,
отступов в отрендеренном SQL нет. Ответ тот же **символ в символ** (сверка старой и новой версии: до 312
случаев — логины, юниты, разрезы, оси, глубина, запасные режимы — на ClickHouse 24.8 с Nullable и без,
с настройками кластера и на 26.9; старый анализатор — проверками датасета: те же строки, что у нового). Разбор в Proteus: форматирование 9,2 → 1,8 с, разбор на ключ кеша
2,05 → 0,73 с, на одно «Применить» 18,6–20,5 → 5,0–6,2 с плюс ClickHouse. ClickHouse не медленнее (на
стенде со 100 тыс. сотрудников — быстрее на 0–0,5 с). Логин из ключа кеша никуда не делся — правка
безопасности на месте.

**Чарт:** строка «Обновляю данные…» считает только секунды текущего запроса, без «прошлый ответ».

1. `2. Proteus — датасет hrbp_hub.sql` — датасет `hrbp_hub` → SQL целиком из файла → Save. Колонки те
   же 29, синхронизировать не нужно.
2. `3. Proteus — чарт HRBP HUB.js` — чарт «HRBP HUB» → JS целиком из файла → Save → обновить дашборд.

Порядок любой: формат ответа не менялся (его читает чарт с шестнадцатой поставки).

**Проверить.** «Применить» с разрезом: строка загрузки считает секунды — было ≈20. F12 → Network →
`chart/data`: POST (202) и забор `qc-…` быстрее. И пришлите, пожалуйста, две строки из SQL Lab — по ним
следующий шаг: сниппет «Сколько считал ClickHouse» (п. 6) отделит время ClickHouse от времени Proteus, а

на стенде почти всё время ClickHouse — планирование запроса, и при старом анализаторе (0) оно в 3 раза

### 07.10, семнадцатая поставка — **срочно: кеш Proteus был общим для всех пользователей** (файл 2)

**Что случилось.** Proteus — это Superset 2. Логин он кладёт в ключ кеша результата, только если видит
`current_username()` внутри `{{ … }}` в SQL датасета. У нас логин брался внутри `{% set me = … %}` —
такой вызов Proteus не видит, и ответ кешировался **общим на всех**: кто открыл борд с теми же
фильтрами вторым, мог получить ответ первого — чужую зону (HRBP — зону админа, админ — зону HRBP), пока
жил кеш. Нашли в соседнем отчёте, у нас то же — во всех поставленных версиях датасета. В ответе —
агрегаты по юнитам (численность, метрики, имена юнитов и HRBP), строк по отдельным сотрудникам нет.

**Закрыть сейчас — одна строка в том датасете, что стоит у вас** (любой версии; чарт не трогать):

1. Proteus → датасет `hrbp_hub` → «Редактировать» → SQL. Найдите строку

   ```
         WHERE login = {{ qs(me) }}
   ```

   и замените её на

   ```
         WHERE login = {{ qs((current_username() or '')|string|trim|lower) }}
   ```

2. Save. Колонки те же. Сохранение меняет дату изменения датасета, а она входит в ключ кеша — старые
   общие записи больше не используются.

Или целиком файлами: сначала файл 3, затем файл 2 (порядок — как в шестнадцатой поставке ниже); в файле 2
правка уже есть. Отчёт от правки не меняется: SQL после подстановки логина тот же, символ в символ.

**Проверить.** Борд с одинаковыми фильтрами под двумя логинами (вы и коллега): F12 → Network → фильтр
`chart/data` → ответ запроса → поле `cache_key` (при асинхронной загрузке — то же число в имени `qc-…`). У
разных логинов ключи должны **различаться**; до правки они совпадали. Роль и зона в шапке отчёта — свои.

**Параграф 17 «Обновить кеш борда»** в ноуте выключен. Если вы его включали: до правки он наполнял общий
кеш ответом r.kazantsev — его получали все, кто открывал борд с фильтрами по умолчанию. После правки он
греет кеш только для r.kazantsev — держите выключенным.

1. Новый чарт на датасете `hrbp_hub`, тип **ECHARTS**, имя «HRBP HUB».
2. **Измерения** — все 29 колонок, точными именами, в любом порядке:

   Мер нет. Сортировки нет. **Лимит строк — 50 000** (Proteus режет ответ лимитом молча; у
   супер-HRBP на всю компанию ответ — тысячи строк). Серверная пагинация — выкл.
   Что значит каждое поле — `proteus/FIELDS.md` в репозитории.
3. JS — файл 3 целиком. Сохранить.
4. Дашборд «HRBP HUB»: чарт во всю ширину, высота — сколько не жалко (1 100–1 400 px);
   внутри чарт прокручивается сам.
5. **Кросс-фильтры: чарт должен фильтровать САМ СЕБЯ.** Без этого «Применить» (юнит, HRBP,
   разрезы), «Открыть юнит» и «Показать» у цели не применяются —
   через 45 секунд чарт сам скажет об этом жёлтой плашкой. Мышкой в интерфейсе это не
   настраивается: у нового дашборда кросс-фильтры выключены, а чарт исключён из своего же
   фильтра. Правится JSON-метаданными дашборда (так настроен рабочий борд 59922 Proteus Adoption):
   1. **id чарта:** меню чарта «⋮» → «Редактировать график» — число после `slice_id=`
      в адресе. Дальше вместо `ID` — это число.
   2. На дашборде «…» (справа вверху) → «Редактировать свойства» (Edit properties) →
      «Дополнительно» (Advanced) → «JSON метаданные».
   3. `"cross_filters_enabled"` → `true` (нет такого ключа — добавьте строку
      `"cross_filters_enabled": true,`).
   4. Блок `"chart_configuration"` замените целиком (нет — добавьте):
      ```json
      "chart_configuration": {
        "ID": {
          "id": ID,
          "crossFilters": {
            "scope": {"rootPath": ["ROOT_ID"], "excluded": []},
            "chartsInScope": [ID]
          }
        }
      },
      ```
      Главное здесь — пустой `"excluded": []`: по умолчанию в нём стоит сам чарт, и
      свой фильтр до него не доходит. В ключе `"ID"` число в кавычках, в остальных местах — без.
   5. Сохранить свойства → «Сохранить» дашборд → обновить страницу.
   Проверка: «Фильтры» → значение разреза → «Применить» — чарт перерисовывается за секунды, жёлтой плашки нет.
   Нативные фильтры дашборда не нужны: все фильтры — внутри чарта.
6. CSS (файл 4): убирает белое поле вокруг чарта и строку шапки чарта Proteus — без него отчёт
   выглядит серым прямоугольником в белой рамке. id чарта 800919 уже вписан; если чарт другой —
   замените 800919 на его id во всех местах.
7. Доступ к дашборду выдайте HRBP как обычно: что каждый видит, решает не Proteus,
   а таблица доступа внутри датасета (своя зона; супер-HRBP и админы — вся компания).
8. Когда борд опубликован — в ноуте включите «Обновить кеш борда», подставив slug.

## 5. Цели (KPI)

Цели живут в параграфе «KPI · реестр целей»: одна строка INSERT = одна цель.
Строку не нужно писать руками: в отчёте откройте нужный юнит → вкладка **«Цели»** →
блок «Новая цель»: метрика, значение, дата начала, комментарий → «Скопировать».
Разрезы цели берутся из строки фильтров (одно значение разреза — в правило,
мультивыбор — «все»). Строку вставьте в INSERT параграфа и перезапустите ноут.
Снять цель — удалить строку или закрыть её датой `valid_to`.

Как цель работает: действует на юнит и всю ветку вниз, пока ниже не встретится своя;
правило с разрезом видно, только когда в фильтрах выбран ровно этот разрез
(в реестре — статус «ждёт разреза», кнопка «Показать» выставит юнит и разрезы сама).
Целей нет у «Численности» и «Non regrettable текучести»: у них «больше» не значит «лучше».
