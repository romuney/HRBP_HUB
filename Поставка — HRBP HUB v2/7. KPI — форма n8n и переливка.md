# KPI в HRBP HUB — форма n8n, DLH и переливка в ClickHouse

Ответ на «Инструкцию агенту фронта: форма кастомных KPI» (ИНСТРУКЦИЯ-KPI-ФОРМА.md). Здесь — что делает отчёт,
какой должна стать форма (v2), что поменять в `build_kpi_flow.py`, в таблице DLH и в переливке.

## 1. Как это работает для HRBP

Вкладка **«KPI»** в отчёте:

- **«Все KPI»** — таблица целей на юнитах зоны HRBP и выше по дереву: юнит, метрика (по-человечески:
  «Regrettable текучесть», а не `rg`), цель, для кого (разрезы), срок, статус («в фокусе», «ждёт разреза»,
  «с …», «истекла»), автор и комментарий. У своих целей — «Показать», «Изменить», «Удалить».
- **«+ Новый KPI»** — форма прямо в отчёте: юнит (выбранный в «Фильтрах»), метрика выпадающим списком из пяти
  понятных названий, цель, срок (по умолчанию — с 1 января текущего года, «по» пусто — без даты окончания), разрезы — те, что
  применены в «Фильтрах» отчёта (показаны чипами, поменять — в «Фильтрах»), комментарий. Рядом — «Сейчас у юнита — 5,1 %, база — 6,5 %».
- Отчёт собирает **ссылку на форму n8n со всеми заполненными полями** — кнопка «Открыть форму»: **правой кнопкой
  мыши → «Открыть ссылку в новой вкладке»** (подсказка — под кнопкой; обычный клик отчёт перехватывает и
  напоминает про правую кнопку). Запасной путь — «Скопировать ссылку» и вставить в адресную строку новой
  вкладки. HRBP проверяет форму и нажимает «Отправить». Через ≤ 30 минут (переливка) цель в отчёте.
- «Изменить» и «Удалить» дают такую же ссылку, но с действием и **ID цели** — новая строка в DLH с тем же
  `rule_id`; отчёт берёт последнюю версию.

Песочница чарта не пускает ни сеть, ни попапы (раздел 2 вашей инструкции), поэтому чарт только собирает ссылку.
«Открыть форму» — обычная ссылка `<a href target=_blank>`: клик и Ctrl/Cmd+клик песочница бы заблокировала
(а клик без `target` открыл бы форму вместо отчёта в его iframe), поэтому их чарт перехватывает. Пункт контекстного
меню «Открыть ссылку в новой вкладке» — действие самого браузера, не скрипта, флаг `allow-popups` ему не нужен.
**На бою это надо проверить один раз** (стенд не умеет кликать контекстное меню): не откроется — остаётся
копирование. Копирование — `execCommand('copy')`, запасной путь — `navigator.clipboard`; если браузер не дал,
ссылка остаётся выделенной: Ctrl+C. Отдельный markdown-чарт не нужен.

## 2. Форма v2 — поля

Prefill-ключ = подпись поля **точно** (регистр, пробелы, скобки). Порядок в prefill не важен; номер поля важен
только для `field-N` в multipart (тесты curl).

| # | Подпись (prefill-ключ) | Тип | Обяз. | Значения | Что пишем в DLH |
|---|---|---|---|---|---|
| 0 | `Действие` | dropdown | да | `Добавить` (по умолчанию), `Изменить`, `Удалить` | `op` = `add` / `update` / `delete` |
| 1 | `ID цели` | text | нет | пусто при «Добавить»; при «Изменить» / «Удалить» — `rule_id` из отчёта | `rule_id` (пусто → `uuid()`) |
| 2 | `ID юнита` | text | да | id юнита из справочника | `unit_id` |
| 3 | `Юнит` | text | нет | название юнита — чтобы человек видел, на что ставит | `unit_nm` (необязательно) |
| 4 | `Метрика` | dropdown | да | 5 названий — таблица ниже | `metric_id` = ключ |
| 5 | `Целевое значение` | number | нет* | число, точка — разделитель | `target` |
| 6 | `Действует с (ГГГГ-ММ-ДД)` | date | нет* | `2026-10-01` | `valid_from` |
| 7 | `Действует по (ГГГГ-ММ-ДД)` | date | нет | пусто — по актуальную дату | `valid_to` (пусто → NULL) |
| 8 | `Покраска` | text | нет | `все` или значение | `f_paint` |
| 9 | `IT / nonIT` | text | нет | `все` или значение | `f_it` |
| 10 | `Стрим` | text | нет | `все` или значение | `f_stream` |
| 11 | `Специализация` | text | нет | `все` или значение | `f_spec` |
| 12 | `Штат / не штат` | text | нет | `все` или значение | `f_staff` |
| 13 | `Тип численности` | text | нет | `все` или значение | `f_hct` |
| 14 | `Ваш логин (например r.ivanov)` | text | да | логин — подставляет отчёт | `author` |
| 15 | `Комментарий` | textarea | нет | | `note` |

\* Не обязательны, потому что при «Удалить» их нет. Отчёт не даст собрать ссылку «Добавить» / «Изменить» без
числа и даты «с».

**Шесть полей разрезов вместо пары «Разрез + Значение»:** цель может быть сразу на нескольких разрезах
(например, HQ + IT), а значение не надо набирать руками — отчёт подставляет точное значение из своих
выпадающих списков. Поля оставить текстовыми: списки значений меняются вместе с данными, и дропдаун формы
пришлось бы пересобирать. Подписи совпадают с подписями фильтров в отчёте.

### Метрика: подпись → ключ (`METRICS` в `build_kpi_flow.py`)

Цели ставятся только на метрики со «стороной лучше» — не на численность и не на non-regrettable (у неё
ориентира нет).

| Подпись в форме | `metric_id` | лучше |
|---|---|---|
| `Закрепляемость новичков · 3 мес` | `retention_new_3` | выше |
| `Закрепляемость новичков · 6 мес` | `retention_new_6` | выше |
| `Regrettable текучесть` | `regret` | ниже |
| `Незаполненные причины увольнений` | `exit_reasons` | ниже |
| `% джунов в команде` | `jun_team` | выше |

Цель в процентах числом: 3,5 % → `3.5`. Отчёт понимает и старые коды v1 (`rg`, `nrg`, `nr`, `jun`, `r3n`, `r6n`),
и подписи — строки, записанные формой v1, не пропадут.

## 3. Ноды флоу

**Set** (вместо «Set разрезы»):

```
op       = {Добавить: 'add', Изменить: 'update', Удалить: 'delete'}[Действие] || 'add'
rule_id  = (ID цели || '').trim()            // пусто → uuid() в INSERT
metric   = METRICS[Метрика] || Метрика       // подпись → ключ
f_X      = ['', 'все', 'all'].includes((поле X || '').trim().toLowerCase()) ? 'all' : (поле X).trim()
           // X: paint ← «Покраска», it ← «IT / nonIT», stream ← «Стрим», spec ← «Специализация»,
           //    staff ← «Штат / не штат», hct ← «Тип численности»
```

**Пустое «Действует по»** пишется NULL (как сейчас, `NULLIF`). Отчёт читает его как «по актуальную дату»: цель
действует по последний закрытый месяц данных и сама продлевается с каждым новым месяцем. Старое «бессрочно»
`2099-12-31` отчёт понимает так же.

Если `op` ≠ `add`, а `ID цели` пуст — это ошибка человека (ссылку из отчёта так не собрать): лучше остановить
флоу с текстом «Для изменения и удаления нужен ID цели — возьмите ссылку из отчёта».

**Trino INSERT** — к вашему добавить `op` и `unit_nm`, `rule_id` — из формы, если он есть:

```sql
INSERT INTO dl.usr_cross_data.hrbp_hub_kpi
(rule_id, op, unit_id, unit_nm, metric_id, target, f_paint, f_it, f_stream, f_spec, f_staff, f_hct,
 valid_from, valid_to, author, note, ts_inserted)
VALUES (
  COALESCE(NULLIF('<rule_id>', ''), CAST(uuid() AS varchar)),
  '<op>',
  '<ID юнита>', NULLIF('<Юнит>', ''), '<metric>',
  CAST(NULLIF('<Целевое значение>', '') AS double),
  '<f_paint>', '<f_it>', '<f_stream>', '<f_spec>', '<f_staff>', '<f_hct>',
  CAST(NULLIF('<Действует с>', '') AS date),
  CAST(NULLIF('<Действует по>', '') AS date),
  NULLIF('<Логин>', ''),
  NULLIF('<Комментарий>', ''),
  CAST(current_timestamp AS timestamp(6))
)
```

Экранирование `'` → `''` — как сейчас. Строка «Удалить» тоже пишется целиком (юнит и метрика из ссылки):
в журнале видно, что удалили.

**Таблица DLH** — один раз:

```sql
ALTER TABLE dl.usr_cross_data.hrbp_hub_kpi ADD COLUMN op varchar;
ALTER TABLE dl.usr_cross_data.hrbp_hub_kpi ADD COLUMN unit_nm varchar;   -- необязательно
```

Старые строки с `op = NULL` отчёт считает добавлениями.

## 4. Переливка DLH → ClickHouse

- Цель: `prod_proteus.hrbp_hub_kpi`, раз в 30 минут, **целиком (replace)**, все колонки как в DLH, включая
  `op` и `ts_inserted`. Таблица маленькая — журнал правок, тысячи строк.
- **Не схлопывать журнал** при переливке: последнюю версию правила (`ORDER BY ts_inserted DESC LIMIT 1 BY rule_id`)
  и пропуск удалённых делает датасет. Так «Изменить» и «Удалить» работают без логики в переливке.
- `unit_path` и `unit_rk` — можно NULL: зона цели считается по справочнику юнитов отчёта, не по ним.
- Массивов в таблице нет — `array_type_cast` не нужен.
- Ноут HRBP HUB с этой поставки **не выгружает** `hrbp_hub_kpi` (параграф 15): иначе каждый запуск ноута затирал бы
  цели из формы. Права владельцев на таблицу — по-прежнему в параграфе 16.
- Если в таблице ClickHouse ещё нет `op` или `ts_inserted`, датасет не падает (читает их матчером): каждая строка —
  отдельная цель, удалений нет. Как только колонки приедут — включится журнал.

Цели из реестра ноута (параграф 12, если там что-то было) один раз перенести в DLH — отправить формой или
INSERT'ом с `op = 'add'`.

## 5. Ответы на пункт 10 вашей инструкции

1. **Справочник значений разрезов.** Не нужен в форме: отчёт подставляет значения из своих выпадающих списков,
   а они — из данных отчёта (`hrbp_hub_base`), то есть ровно те строки, с которыми цель потом сравнивается.
   Если всё же нужен список — SQL Lab, база CROSS:
   ```sql
   SELECT 'paint' AS cut, paint AS v FROM prod_proteus.hrbp_hub_base GROUP BY v
   UNION ALL SELECT 'it', it FROM prod_proteus.hrbp_hub_base GROUP BY it
   UNION ALL SELECT 'stream', stream FROM prod_proteus.hrbp_hub_base GROUP BY stream
   UNION ALL SELECT 'spec', spec FROM prod_proteus.hrbp_hub_base GROUP BY spec
   UNION ALL SELECT 'staff', staff FROM prod_proteus.hrbp_hub_base GROUP BY staff
   UNION ALL SELECT 'hct', hct FROM prod_proteus.hrbp_hub_base GROUP BY hct
   ORDER BY cut, v
   ```
2. **Состав prefill.** Отчёт заполняет всё: действие, ID цели, юнит (id и название), метрику, цель, срок
   (по умолчанию — с 1 января текущего года, «Действует по» пусто), разрезы (из «Фильтров» отчёта), комментарий и логин (`current_username()` из датасета).
   Ссылка — кнопкой «Открыть форму» (правой кнопкой мыши → новая вкладка) или «Скопировать ссылку» в самом отчёте.
3. **Дубли.** Ключ — `rule_id`: «Изменить» и «Удалить» пишут новую строку с тем же `rule_id`, отчёт берёт
   последнюю по `ts_inserted`. Повторное «Добавить» — новая цель (новый uuid): в таблице «Все KPI» их будет
   две, лишнюю удаляют. Схлопывать по `unit_id + metric_id + f_* + период` не советую: две цели с разными
   сроками на одну метрику — нормальный случай.
4. **Валидация юнита и автора.** В отчёте цель видна только на юнитах зоны HRBP (и выше по дереву) —
   чужие и несуществующие `unit_id` не приезжают никому. Слабое место — форма открыта: знающий `rule_id` может
   «изменить» чужую цель. Если это важно — следующим шагом датасет может принимать правку только от автора с
   доступом к юниту (`hrbp_hub_access`); скажите — сделаю.

## 6. Проверка

Форма v2, curl (номера полей — по таблице раздела 2):

```bash
curl -X POST "https://n8n.t-tech.team/form/hrbp-kpi" \
  -F 'field-0=Добавить' -F 'field-2=7411' -F 'field-3=Розничный бизнес' \
  -F 'field-4=Regrettable текучесть' -F 'field-5=3.5' \
  -F 'field-6=2026-10-01' -F 'field-7=2027-09-30' \
  -F 'field-8=HQ' -F 'field-9=все' -F 'field-10=все' -F 'field-11=все' -F 'field-12=все' -F 'field-13=все' \
  -F 'field-14=r.kazantsev' -F 'field-15=тест'
```

После переливки — SQL Lab, база CROSS: последние версии целей.

```sql
SELECT rule_id, op, unit_id, metric_id, target, f_paint, f_it, f_stream, f_spec, f_staff, f_hct,
       valid_from, valid_to, author, ts_inserted
FROM prod_proteus.hrbp_hub_kpi
ORDER BY ts_inserted DESC LIMIT 1 BY rule_id
```

В отчёте: вкладка «KPI» → цель в таблице «Все KPI»; «Показать» откроет юнит с разрезами цели, цель — в
«Сводке» вместо базы.

## 7. Пока форма ещё v1

Ссылка из отчёта откроет и старую форму: заполнятся совпавшие поля (ID юнита, цель, даты, логин,
комментарий). Метрику (коды v1) и разрез придётся выбрать руками, «Изменить» и «Удалить» не сработают — у v1 нет
полей «Действие» и «ID цели». Строки v1 отчёт показывает.
