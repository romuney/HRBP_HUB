# HRBP HUB — как устроено (реализация)

Отчёт для HRBP: сводка метрик юнита, команды вглубь оргструктуры до 12-го уровня,
трансформеры по любому разрезу и атрибуту, реестр целей с наследованием вниз по
оргструктуре. В Proteus это **один чарт на одном датасете**: всё, что в макете
разнесено по полке фильтров, шапке, четырём вкладкам и окну KPI, живёт в одном виджете.

```
GP: mdm_employee_structure_d + regrettable-разметка + причины увольнений + резиденция
        │  ноут Helicopter «HRBP HUB» (helicopter/HRBP HUB.yaml, 20 параграфов)
        ▼
GP: hrbp_hub_calendar · unit · access · kpi · cube · base · attr
        │  gp_to_click (replace) — параграф «Выгрузка в ClickHouse»
        ▼
ClickHouse: prod_proteus.hrbp_hub_*            (база Proteus CROSS)
        │  датасет hrbp_hub (proteus/hrbp-hub.data.sql): Jinja + current_username()
        ▼
Proteus: чарт «HRBP HUB» (proteus/hrbp-hub.chart.js) — кросс-фильтр на самого себя
```

Что где лежит:

| Путь | Что это |
|---|---|
| `helicopter/paragraphs/` | параграфы ноута — источник правды; `helicopter/build.py` собирает из них YAML |
| `helicopter/HRBP HUB.yaml` | ноут для импорта в Helicopter |
| `proteus/hrbp-hub.data.sql` | SQL датасета `hrbp_hub` |
| `proteus/hrbp-hub.chart.js` | JS чарта (ECHARTS, контракт скилла proteus-echarts-builder) |
| `proteus/FIELDS.md` | 29 полей «Измерений» и ручные настройки чарта |
| `stand/` | стенд: синтетический мир → PostgreSQL (как GP) → chdb (ClickHouse 24.8 и 26.9) → датасет → регресс, живая страница чарта, нагрузка на 100 тыс. |
| `Поставка …/` | нумерованные файлы «что куда вставлять» + `0. Инструкция.md` |

## 1. Главные решения

1. **Числитель и знаменатель, а не проценты.** Любая цифра отчёта — `Σ num / Σ den`.
   Поэтому строки куба можно складывать как угодно: юниты зоны, −1, −2, базу,
   значения разреза — и получать верный процент без пересчёта событий.
2. **Время — позиция в массиве.** Окно фиксировано: 24 месяца (прошлый и текущий
   календарный год) и 24 закрытые недели. Каждая строка несёт массивы `m_*` и `w_*`
   по 24 значения. Переключатели «год / 12 недель» и спарклайны не ходят в базу.
3. **Окна считаются в GP.** Текучесть за 12 мес, незаполненные причины за 3 мес,
   созревшие когорты новичков — суммы событий за окно на каждой строке куба.
   Сумма окон по строкам = окно суммы, так что складывать можно и дальше.
4. **Оргструктура — путь в строке.** Каждая строка куба несёт путь юнита от
   корня (`path`, id = первые 12 знаков md5 от mapped rk). Уровни — как в
   ультраширокой витрине: `lvl1` (компания) и `lvl3…lvl12`. `lvl2` пропускается,
   глубже 12-го — обрезается: сотрудник 13-го уровня считается в своём юните
   12-го. Выборка поддерева — `hasAny(path, [юниты])`, уровень −1 / −2 — элемент
   пути после выбранного.
5. **Один запрос на смену юнита, разрезов или оси.** Ответ датасета везёт сразу
   сводку, дерево «Команд» на 3 уровня вниз, базу, фасеты фильтров, справочник
   юнитов, HRBP, цели и календарь. Вкладки, раскрытие строк «Команд», клики по
   командам, наследование целей, светофор — в JS по уже приехавшим строкам, без
   догрузки. Отдельным запросом идёт только поиск юнита по большой зоне; глубже трёх
   уровней «Команд» — «Открыть юнит» (смена юнита отчёта, тот же один запрос). Фильтры
   строки (юнит, зона HRBP, разрезы) копятся и уходят одним запросом по «Применить».
6. **Доступ внутри датасета.** `current_username()` → `hrbp_hub_access` → корни
   зоны. Юниты вне зоны не приезжают ни в каком виде, запрос чужого юнита
   откатывается на свою зону.
7. **Масштаб — агрегат, а не сотрудники.** Неагрегированный источник при
   ≈100 тыс. сотрудников — ≈100 тыс. строк на каждую точку (48 точек ≈ 5 млн).
   Куб — одна строка на путь юнита × 6 разрезов с массивами 24 + 24: на всю
   компанию, по оценке стенда, ≈40–60 тыс. строк. Запрос читает только ветку
   выбранного юнита (куб отсортирован по `path_s`), база сравнения — из отдельной
   маленькой таблицы, справочник большой зоны — окрестностью выбранного юнита.

## 2. Ноут Helicopter

Расписание — ежедневно после обновления `mdm_employee_structure_d`. Параграфы:

| # | Параграф | Что делает | Выход |
|---|---|---|---|
| 00 | Описание | источники, таблицы, порядок | — |
| 01 | Актуальность источников | `tf.tables_wait` по четырём источникам | — |
| 02 | HH · параметры | дата данных, последний закрытый месяц и неделя, грейс 30 дней для причин, rk юнита супер-HRBP, тип «Активная», шаблоны джунов, админы | `hh_param*` |
| 03 | HH · календарь | 24 месяца + 24 недели (и история под окна) | `hrbp_hub_calendar` |
| 04 | HH · строки источника | один проход по базе: строки концов слотов, дней найма/увольнения/перехода в активные; путь юнита (`lvl1` + `lvl3…lvl12`), разрезы, атрибуты | `hh_rows` |
| 05 | HH · справочник юнитов | все узлы путей: имя, родитель, уровень, текущий ли, численность поддерева сейчас, число детей, размер поддерева, rk | `hrbp_hub_unit` |
| 06 | HH · зоны HRBP и доступ | корни HRBP (как в «Связях и подчинениях»), подъём до общего юнита, супер-HRBP, админы | `hrbp_hub_access` |
| 07 | HH · увольнения | regrettable / non-regrettable (джойн разметки по сотруднику и дате), причина не заполнена | `hh_fire` |
| 08 | HH · когорты найма | новички от company_hire_dt и от active_hire_dt | `hh_cohort` |
| 09 | HH · события по слотам | вклад строки в компонент метрики в слоте | `hh_evt` |
| 10 | HH · куб по разрезам | путь × 6 разрезов → массивы с окнами; база — то же без пути | `hrbp_hub_cube`, `hrbp_hub_base` |
| 11 | HH · куб атрибутов | то же × атрибут (11 осей), только месяцы | `hrbp_hub_attr` |
| 12 | KPI · реестр целей | **правится руками**: одна строка INSERT = одна цель | `hh_kpi_src` |
| 13 | KPI · цели для отчёта | rk → id юнита, пустые разрезы → 'all', «бессрочно» = 2099-12-31 | `hrbp_hub_kpi` |
| 14 | HH · проверки | стоп-проверки делением на ноль + диагностика | — |
| 15 | Выгрузка в ClickHouse | `gp_to_click(..., upload_mode='replace')` семи таблиц | `prod_proteus.hrbp_hub_*` |
| 16 | Доступ к таблицам в Proteus | `set_table_owners` для команды отчёта | — |
| 17 | Обновить кеш борда | выключен до публикации борда | — |
| 18 | Диагностика источников | выключен; значения разрезов, покрытие разметки | — |
| 19 | HH · удалить времянки | чистка `hh_*` | — |

Стоп-проверки (14) роняют ноут до выгрузки, если: дубли сотрудника в дне, массивы
не по 24, численность куба ≠ численности источника, база ≠ сумме куба, путь длиннее
11 узлов (компания + 10 уровней), юнит куба не в справочнике, пустой доступ.
Правила целей с неизвестным rk или метрикой печатаются списком.

## 3. Таблицы ClickHouse (`prod_proteus`)

Все колонки после `gp_to_click` — Nullable, поэтому датасет везде пишет `ifNull`.
Массивы GP становятся массивами ClickHouse только при `array_type_cast=True` (unit, cube,
attr, base); без флага массив приезжает строкой. Стенд (`stand/ch.py load`) читает флаги
из параграфа «Выгрузка в ClickHouse» и повторяет это.

### `hrbp_hub_calendar` — что значит позиция в массиве · ORDER BY (grain, idx)

| Колонка | Тип | Смысл |
|---|---|---|
| grain | String | `m` — месяц, `w` — неделя |
| idx | Int32 | 0…23 — позиция в массивах |
| slot_start, slot_end | Date | границы слота (неделя пн–вс) |
| is_closed | Int32 | 1 — слот закрыт (конец ≤ даты данных) |
| data_dt | Date | дата данных источника |

Месяцы: 0…11 — прошлый календарный год, 12…23 — текущий (год последнего закрытого
месяца), незакрытые — пустые. Недели: 23 — последняя закрытая.

### `hrbp_hub_unit` — справочник юнитов · ORDER BY (id)

| Колонка | Тип | Смысл |
|---|---|---|
| id | String | 12 знаков md5(mapped rk) — id узла во всех таблицах |
| rk | String | исходный mapped rk — по нему ставят цели |
| nm | String | имя (по самой свежей строке) |
| lvl | Int32 | номер уровня из источника: 1 — компания, 3…12 — уровни ультраширокой (2 не бывает) |
| pid | String | родитель (для юнита 3-го уровня — компания) |
| path | Array(String) | путь от корня до узла, до 11 id |
| is_current | Int32 | узел есть в срезе даты данных |
| hc_now | Int32 | численность поддерева на дату данных |
| kids_n | Int32 | сколько у узла дочерних юнитов — каретка в выборе юнита, даже когда дети не приехали |
| sub_n | Int32 | сколько юнитов в поддереве вместе с самим узлом — по нему датасет решает, отдавать ли справочник зоны целиком |
| last_dt | Date | последняя дата, где узел встречался |

### `hrbp_hub_access` — доступ · ORDER BY (login)

| Колонка | Тип | Смысл |
|---|---|---|
| login | String | логин Proteus (нижний регистр) |
| hrbp_rk, hrbp_nm | String | сотрудник-HRBP |
| role | String | `super` (вся компания), `admin` (вся компания), `hrbp` (своя зона) |
| root_id | String | корень зоны; строк на логин — сколько корней |

### `hrbp_hub_kpi` — цели · ORDER BY (unit_id)

| Колонка | Тип | Смысл |
|---|---|---|
| rule_id | String | код правила |
| unit_id, unit_rk, unit_path | String, String, String | юнит цели; `unit_path` выгружается без `array_type_cast` и в ClickHouse — строка `{a,b,c}`, датасет её не читает (путь юнита цели — из `hrbp_hub_unit`) |
| metric_id | String | retention_new_3, retention_new_6, regret, exit_reasons, jun_team |
| target | Float64 | цель в единицах метрики (3.5 = 3,5 %) |
| f_paint … f_hct | String | разрезы, при которых цель действует; `all` — при любых |
| valid_from, valid_to | Date | срок; бессрочно = 2099-12-31 |
| author, note | String | кто и зачем |

### `hrbp_hub_cube` — куб · ORDER BY (path_s)

| Колонка | Тип | Смысл |
|---|---|---|
| path_s, path | String, Array(String) | путь юнита строкой и массивом (до 11 узлов) |
| leaf | String | последний узел пути |
| paint, it, stream, spec, staff, hct | String | 6 разрезов численности (пусто = `-`) |
| m_* (16) | Array(Int32) | 24 месяца: hc, jun, rg, nrg, hcw, nr, r3n, r3d, r6n, r6d, r3an, r3ad, r6an, r6ad, hire, fire |
| w_* (16) | Array(Int32) | то же по 24 неделям |

Ветка юнита лежит подряд: у всех её строк `path_s` начинается с пути юнита.
Поэтому датасет читает не весь куб, а диапазон `[путь, путь + '0')`.

### `hrbp_hub_base` — база сравнения · ORDER BY (paint, it, stream, spec, staff, hct)

Вся компания по 6 разрезам **без пути**: те же `m_*` и `w_*`, что в кубе, — сумма
куба по разрезам (стоп-проверка сверяет). Ориентир «вся компания под теми же
разрезами» берётся отсюда за несколько тысяч строк, а не суммой всего куба на
каждый клик.

### `hrbp_hub_attr` — куб атрибутов · ORDER BY (attr_k, path_s)

Те же ключи + `attr_k` (grade, seniority, exp, gender, age, office, work, head,
legal, macro, city) и `attr_v`; только месячные массивы `m_*`.

Разрезы (`filter-fields.md`): paint = `emp_specialization_oper_code`,
it = `emp_specialization_it_code`, stream = `emp_stream_desc`,
spec = `emp_specialization_desc`, staff = «Штат» для `employment_relation_type_desc =
'Штатный сотрудник'`, иначе «Не штат», hct = `active_type_nm`.

## 4. Метрики

| Метрика | Числитель | Знаменатель | Окно | Лучше |
|---|---|---|---|---|
| Закрепляемость новичков · 3 мес | r3n — дожили до 3 мес | r3d — созрели в окне | 3 мес / 13 нед | выше |
| Закрепляемость новичков · 6 мес | r6n | r6d | 3 мес / 13 нед | выше |
| Regrettable текучесть | rg — regrettable-увольнения | hcw / 12 (/ 52) — средняя численность | 12 мес / 52 нед | ниже |
| Non regrettable текучесть | nrg | hcw / 12 (/ 52) | 12 мес / 52 нед | нейтральна |
| Незаполненные причины увольнений | nr — без причины, 30+ дней | hc на конец | 3 мес / 13 нед | ниже |
| Численность | hc на конец слота | — | — | нейтральна |
| % джунов в команде | jun (seniority ILIKE intern% / jun%) | hc | — | выше |

- Численность — `active_employee_flg = 1` на последний день слота (все, кроме «Декрет»).
- Увольнение — строка дня `company_fire_dt`; юнит и разрезы — на эту дату.
- Когорта: новичок созрел, когда найм + 3 (6) месяцев (91 / 182 дня для недель)
  попал в окно; дожил — не уволен к этой дате. Незрелые не считаются.
  При типе численности ровно «Активная» база — `active_hire_dt` (`r3an/r3ad…`),
  иначе `company_hire_dt`.
- Нейтральные метрики не красятся и целей не имеют.

## 5. Датасет `hrbp_hub`

Вход — кросс-фильтры, которые эмитит сам чарт (самовлияние включено):

| Носитель | Что несёт | Проверка в Jinja |
|---|---|---|
| `unit_f` | id юнитов отчёта (≤ 50) | вне зоны → откат на свою зону |
| `paint_f` `it_f` `stream_f` `spec_f` `staff_f` `hct_f` | значения разрезов (≤ 200 на разрез) | экранирование строк |
| `tr_f` | ось трансформеров | белый список из 17 осей |
| `depth_f` | глубина «Команд»: `all` — все уровни (нет носителя — 3 уровня). **В запасе:** с 29.09 чарт его не шлёт — глубже трёх уровней ведёт «Открыть юнит» | `all` действует, только если в ветке юнита ≤ `ALL_MAX` = 1 000 юнитов |
| `q_f` | строка поиска юнита по имени (≤ 60 знаков) | ищется только в зоне пользователя |

Носители в SELECT не выводятся. `filter_values` при сохранении датасета отдаёт
AlwaysTrueObject — списки собираются циклом, дефолт — зона пользователя.

Выход — 29 колонок, строки разных ролей:

| role | id | pid | n | j / массивы |
|---|---|---|---|---|
| meta | — | — | — | JSON: логин, роль, корни, область, эхо фильтров (`req_unit`, `depth_req`, `q`, разрезы, ось), отданная глубина `depth` (`3` / `all`), юнитов в ветке `scope_n` и порог `all_max`, размер зоны `zone_n`, режим справочника `dict_mode`, база закрепляемости, последний месяц, календарь |
| dict | — | — | число юнитов | `id\tpid\tlvl\thc\tcur\trk\tnm\tkids_n` через `\n` (состав — ниже) |
| hrbps | — | — | число HRBP | HRBP, чьи зоны внутри моей: `login\tимя\tкорни\tчисленность\tпути корней` (путь — id через `/`, пути — через запятую) |
| base | — | — | — | вся компания под теми же разрезами (из `hrbp_hub_base`), m_* и w_* |
| scope | — | — | — | выбранная область, m_* и w_* |
| c | юнит −1 (`·` — прямо в юните) | — | — | m_* и w_* |
| g | юнит −2 (`·` — прямо в −1) | юнит −1 | — | m_* и w_* |
| x | юнит −3 и глубже (`·` — прямо в родителе) | путь родителя от узла −1 через `/` | — | m_* и w_* |
| f | значение | разрез | численность при остальных разрезах | — |
| tr | значение оси | — | — | только m_* |
| kpi | rule_id | юнит | — | `метрика\tцель\t6 разрезов\tс\tпо\tавтор\tкомментарий\trk` |

Массивы — строкой через запятую (так они переживают сериализацию Proteus).
Для зоны из нескольких корней `c` — сами корни, `g` — их дети, `x` — внуки.
`pid` у `x` — путь, а не id родителя: после реорганизации один юнит бывает под
двумя родителями, и его дети считаются отдельно в каждом месте дерева. «·» без
соседей-подразделений не приезжает: «Напрямую в …» нужна только рядом с ними.

Справочник (`dict`): зона до `DICT_FULL_MAX` = 1 500 юнитов приезжает целиком (поиск
в чарте мгновенный); больше — `dict_mode = part`: путь до выбранного юнита с соседями
на каждом уровне, вся выбранная область, если в ней не больше `DICT_FULL_MAX` юнитов
(иначе — отданное дерево «Команд»: 3 уровня или все), дети корней зоны, корни зон HRBP
(для дерева HRBP), юниты с целями и найденное поиском `q_f` (до 60 юнитов с путями,
сначала — внутри выбранной области). Признак `scope_full` в meta: область приехала
целиком — поиск в ней чарт ведёт сам, без запроса. Так выбранная зона HRBP на
100 тыс. сотрудников приезжает полным деревом. Предки корней зоны приезжают всегда —
для пути юнита и наследования целей.

Как запрос держит 100 тыс. сотрудников:

- контекст (доступ, область, глубина, диапазон путей) — цепочка маленьких CTE
  по `hrbp_hub_access` и `hrbp_hub_unit`, юниты берутся по ключу `id IN (…)`;
- куб читается в диапазоне `path_s` выбранной области; вне ветки строки не читаются;
- юнит и всё дерево «Команд» — один проход по ветке (`GROUP BY k1…kD WITH ROLLUP`,
  D = 3, для `depth_f = all` — 10), уровень строки — число непустых ключей; фасеты
  фильтров — без массивов, база — из `hrbp_hub_base`;
- `depth_f = all` (в запасе: чарт его с 29.09 не шлёт) — только для ветки до `ALL_MAX` =
  1 000 юнитов (`sub_n` из справочника): у каждой строки дерева 24 массива по 24 точки,
  и ветка в 1 000 юнитов — ≈2 МБ ответа. Больше — отдаются 3 уровня, в meta `depth = 3`.

Роли доступа: `super` и `admin` видят компанию, `hrbp` — поддеревья своих корней,
без строки в `hrbp_hub_access` приезжает только meta (чарт пишет «нет зоны»).

Совместимость с ClickHouse 24.8 (бой): без коррелированных WITH-алиасов
(CTE-цепочка + CROSS JOIN ctx), без `SETTINGS` внутри, `ifNull` на всех колонках
(в том числе на ключах ROLLUP — на случай `group_by_use_nulls = 1`);
проверено в режимах `prefer_column_name_to_alias = 1`, `join_use_nulls = 1`,
`group_by_use_nulls = 1`, со старым и новым анализатором.

Таблица «Команд»: клик по заголовку любой колонки сортирует соседей внутри каждого
уровня (метрика — сначала по убыванию, «Юнит» — по алфавиту, третий клик — как было,

юниты подсвечены, их предки раскрыты и приглушены. Клик по строке только выбирает её для

строк (место под неё есть в каждой строке) — и в шапке «Динамики» рядом с «Год /
12 недель». Над вкладками «Сводка» и «Команды» — путь юнита отчёта (предки внутри зоны
кликабельны), «↑ Уровнем выше» и «← Назад» (стек переходов, до 10).

Длинные имена юнитов (в бою — на 3–4 строки) идут одной строкой с «…»: в таблице
«Команд» предел — 36 % ширины панели (160–420 px, тянется вместе с разделителем), имя
целиком — в подсказке, у выбранной строки и у находок поиска (совпадение не прячется
за «…»); «ИТОГО» остаётся в одну строку — её имя в пути над таблицей. Так же обрезаются подзаголовок «Динамики» и звенья пути (текущий
юнит пути — целиком). Проверка — `?long=1` живого стенда.
Отступ — 12 px на уровень, не больше 8 ступеней; глубину договаривает подпись
«ур. N · X чел». «Напрямую в …» — сотрудники, закреплённые за самим узлом.

Шапка: название, период, роль. Строка фильтров: **Юнит** (дерево зоны с поиском),
**HRBP** (дерево «кто под кем» с поиском по фамилии, логину и юниту), 6 разрезов
(мультивыбор со счётчиками). Выбор в них копится: изменённый фильтр — с пунктирной
рамкой, кнопка **«Применить · N»** отправляет всё одним запросом, «Отменить»
возвращает применённое. Дальше — метрики для показа, «Только фокусные», «Сбросить»
(сразу, без «Применить»), база. «Открыть юнит» в «Командах», путь юнита и «Показать» у
цели меняют юнит сразу — это действия, а не фильтры; «← Назад» возвращает к юниту до
перехода.

Дерево HRBP строится в чарте по путям корней из строки `hrbps`: HRBP A выше HRBP B,
если каждый корень B лежит внутри какого-то корня A, а не наоборот; из таких A
родитель — самый маленький по численности. Выбор HRBP = его корни как юнит отчёта,
и дальше выбор юнита — внутри его зоны: «Юнит» показывает компактное дерево зоны
(корни с путём сверху, «Вся зона HRBP»), поиск — только в ней; «Вся зона видимости»
внизу списка возвращает всё дерево с отмеченной зоной. HRBP держится, пока область
внутри его зоны (переход в чужую зону его снимает), и восстанавливается после
перезагрузки, если область ровно совпадает с его корнями. Сам HRBP под своим логином
видит только свою зону — по доступу датасета.

Для большой зоны (`dict_mode = part`) у узлов без приехавших детей стоит «N
подразделений — выберите юнит и примените, они подгрузятся», а поиск юнита от 2 букв
сам уходит по всей зоне через полсекунды после ввода, без Enter («Найдено по всей
зоне: N», у каждой находки — путь).

## 10. Что сверить на боевых данных

7. Уровни: сколько юнитов на каждом уровне и есть ли сотрудники глубже 12-го
   (они посчитаны в своём юните 12-го уровня) — проверка 6 файла 5 поставки.
