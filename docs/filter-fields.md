# HRBP HUB — поля для фильтров: макет → витрина `mdm_employee_structure_d`

> **Назначение.** Отдельно зафиксировать поля, которые потребуются для **фильтров
> отчёта**, сопоставив их с реальными колонками основного источника —
> `prod_v_emart.mdm_employee_structure_d`. Это справочник для сборщика витрины:
> какие колонки читать из источника, какие значения допустимы, где значения надо
> сверить с данными.
>
> Фильтры в макете заданы в `data.js` (`FILTER_DEFS`, `PAINTS`, `ITSEGS`,
> `STREAMS`, `SPECS`, `STAFFTYPES`, `HCTYPES`). Подробнее о самих метриках —
> в `business-context.md`; архитектура витрины — в `dataset-spec.md` и
> `data-dictionary.md`.
>
> Схема витрины сверена с Data Detective (`get_table_info`): все поля фильтров
> присутствуют в источнике. Колонки `regrettable_fire_flg`, `non_regrettable_flg`,
> `subordination_lvl` в `mdm_employee_structure_d` **отсутствуют** — они нужны
> метрикам (regret/nonregret) и появляются только в производной ультраширокой
> из внешних джойнов, к фильтрам отношения не имеют.

---

## 1. Фильтры отчёта (из макета)

Фильтры собираются на левой полке (`#shelf`) и работают единым перечнем в двух
местах: как фильтр отчёта и как условие применения KPI в реестре целей.

| Ключ фильтра | Подпись (label) | Атрибут листа | Значения (список) |
|---|---|---|---|
| `paint` | Покраска | `paint` | `all`, HQ, Line, Support |
| `itSeg` | IT / nonIT | `it` | `all`, IT, nonIT |
| `stream` | Стрим | `stream` | `all`, Платформа, Продукт, Данные, Операции, Сопровождение |
| `spec` | Специализация | `spec` | `all`, Разработка, Аналитика, Тестирование, Инфраструктура, Продукт, Поддержка |
| `staffType` | Штат / не штат | `staff` | `all`, staff, nonstaff |
| `hcType` | Тип численности | `hcType` | `all`, core, part, project, intern |

`all` = предиката нет (суммируем всё). В правиле KPI «применить к любой
численности» — отдельная колонка (`f_*`).

Кроме разрезов, в отчёте есть **неразрезные** фильтры:
- **Юнит отчёта** (дерево: `dim_unit` / `dim_unit_closure`) — выбирается в шапке.
- **HRBP** (`scope_hrbp_id`, `scope_hrbp_zone_root_id`) — зона ответственности, RLS.

## 2. Сопоставление с витриной `mdm_employee_structure_d`

Все разрезы читаются **из одной строки источника** по ключу `mdm_employee_rk`
на дату `business_dt`. Фильтрация источника — `last_day_flg = 1` (актуальный срез).

### 2.1. Разрезы численности (6 шт.)

| Разрез (макет) | Колонка витрины | Тип | Значения / маппинг |
|---|---|---|---|
| `paint` (покраска) | `emp_specialization_oper_code` | varchar | HQ, Line, Support |
| `itSeg` (IT / nonIT) | `emp_specialization_it_code` | varchar | IT, nonIT |
| `stream` (стрим) | `emp_stream_desc` | varchar | Платформа, Продукт, Данные, Операции, Сопровождение |
| `spec` (специализация) | `emp_specialization_desc` | varchar | Разработка, Аналитика, Тестирование, Инфраструктура, Продукт, Поддержка |
| `staffType` (штат/не штат) | `employment_relation_type_desc` | varchar | `'Штатный сотрудник'` → staff, всё остальное → nonstaff |
| `hcType` (тип численности) | `active_type_nm` | varchar | `active_type_nm` как есть (значения сверить) |

### 2.2. Юнит отчёта (дерево)

| Назначение | Колонки витрины |
|---|---|
| Лист, где сидит сотрудник | `management_unit_rk`, `mapped_management_unit_nm` |
| Уровень листа | `management_unit_lvl_num` |
| Mapped-цепочка предков 1..13 | `lvl1..lvl13_mapped_management_unit_rk`, `lvl1..lvl13_mapped_management_unit_nm` |

Дерево отчёта строится по mapped-цепочке (см. `01_dim_unit.sql`): узлы = mapped-
юниты уровней 1..13 + сам лист `management_unit_rk`. Путь собирается из
`unit_id`, не из названий.

### 2.3. HRBP (зона/RLS)

| Назначение | Колонки витрины |
|---|---|
| Ключ HRBP | `hrbp_mdm_employee_rk` |
| Логин (для RLS по текущему пользователю) | `hrbp_ad_login` |
| Имя | `hrbp_full_nm` (также `hrbp_last_nm`, `hrbp_first_nm`) |

### 2.4. Период / срез

| Назначение | Колонки витрины |
|---|---|
| Дата среза (подневная история) | `business_dt` |
| Последний отчётный день | `last_day_flg` |
| Последний день месяца | `last_day_of_month_flg` |
| Флаг активной численности (для `headcount`) | `active_employee_flg` |

## 3. Подводные камни и что сверить

1. **`staffType` (`employment_relation_type_desc`).** Маппинг: `'Штатный сотрудник'` → `staff`,
   всё остальное → `nonstaff`. Поле «Описание типа трудовых отношений» (НЕ `legal_employee_flg`).
   Перед сборкой сверить фактический набор значений поля — если есть другие значения кроме
   «Штатный сотрудник» и совместительств, проверить, куда они должны попадать.

2. **`active_type_nm` — значения не сверены.** Комментарий схемы не даёт перечня.
   В макете `hc_type` = core / part / project / intern. Нужно выгрузить distinct
   значений `active_type_nm` из источника и сопоставить с кодами макета
   (возможно, значения полные: «Основной состав», «Совместители», «Проектные»,
   «Стажёры» — как в CH-витрине). Маппинг зафиксировать один раз.

2. **`emp_specialization_oper_code` / `emp_specialization_it_code` — значения
   не сверены.** Комментарии схемы («Отношение специализации к операционной
   деятельности / к IT направлению») не дают перечня значений. Проверить, что
   `oper_code` реально даёт HQ/Line/Support, а `it_code` — IT/nonIT (без лишних
   категорий, которые надо было бы доразметить).

3. **`hrbp_ad_login` протянут на всю историю.** Комментарий: «Используется
   последнее известное значение логина сотрудника на всю историю!». Для RLS по
   текущему пользователю это ок, но при исторических срезах логин может не
   соответствовать факту на ту дату.

4. **`management_unit_lvl_num` протянут по ключу `(mdm_employee_rk,
   management_position_rk)`** — при переносах уровень юнита у листа может
   расходиться с mapped-цепочкой. Для дерева отчёта используем mapped-уровни.

5. **В витрине нет regrettable-флагов и `subordination_lvl`.** Они появляются
   только в производной ультраширокой (`all_employee_add_flags`) из внешних
   джойнов (`usr_cross_data.regrettable_n_non_regrettable_base`). Для фильтров
   не нужны; метрики regret/nonregret строятся на ультраширокой, а не напрямую
   на `mdm_employee_structure_d`.

6. **`seniority` (для `jun_team`).** По схеме значения: `n/a, Junior, Junior+,
   Middle, Middle+, Senior, Senior+, Lead`. Это уточняет jun-маппинг: джуны —
   по `seniority` ∈ {Junior, Junior+} (сопоставление по подстроке/LIKE). Значение
   «Intern» в схеме не упомянуто — сверить фактический перечень перед сборкой.
