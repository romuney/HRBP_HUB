# HRBP HUB — ролевая модель доступа к метрикам

> **Назначение.** Как расчётные метрики (`hub_fact`) связываются с настройкой
> доступов для HRBP: какие роли есть, какие юниты видит каждая роль, как это
> материализуется в витрину и превращается в RLS в Proteus.
>
> **Источник правил — хелик «Связи и подчинения»** (`../Текущие хелики/Связи и
> подчинения.yaml`). Реализация: `sql/greenplum/01_dim_unit.sql` (GP) →
> `hrbp.dim_hrbp_scope` (CH) → условие RLS в Superset. Справочник колонок —
> `data-dictionary.md` § 4.

---

## 0. Коротко

- **Один факт считается один раз** на всех юнитах; доступ — не в метриках,
  а в том, **какие юниты видит пользователь**.
- Роль определяется **зоной HRBP** (назначенный юнит) плюс **супер-привилегией**
  (лид эйчар видит всё).
- RLS фильтрует витрину по `scope_unit_id` через справочник
  `dim_hrbp_scope(hrbp_login → unit_id)`.

---

## 1. Роли (`access_role`)

| `access_role` | Роль | Кто попадает | Видимость юнитов |
|---|---|---|---|
| `спец роль` | назначенный HRBP | HRBP с назначенной зоной | **поддерево своего корня** (root) |
| `лид эйчар` | супер-HRBP | HRBP, над которым нет других HRBP, сидящий в целевом юните | **все юниты компании** |

Обе роли живут в одном справочнике `dim_hrbp_scope` и различаются только
шириной видимости: у `спец роль` — своя ветка, у `лид эйчар` — весь справочник
юнитов (cross join по `dim_unit`). Поэтому для RLS не нужна развилка по роли —
достаточно **проверки принадлежности** `scope_unit_id` зоне пользователя.

---

## 2. Откуда берётся роль: хелик «Связи и подчинения»

Правило ролей строится из одной базы `prod_v_emart.mdm_employee_structure_d`
(срез `last_day_flg = 1`) и двух цепочек:

| Временная таблица хелика | Что даёт | Куда попадает в марте |
|---|---|---|
| `tmp_unit_dict` | справочник юнитов (ключ, имя, уровень) | `dim_unit` |
| `tmp_hierarchy` | плоская иерархия юнит → предок/сам (уровни 1..13) | `dim_unit` / `dim_unit_closure` |
| `tmp_head_chain` | цепочка руководителей сотрудника (уровни 1..13) | супер-детект, флаг подчинения |
| `tmp_unit_lvl2_root` | корень уровня 2 каждого юнита | зона супер-HRBP |
| `tmp_hrbp_roots` | корни зон HRBP (назначенный юнит + уровень + логин) | `dim_hrbp_scope` |
| `tmp_super_hrbp` | детект супер-HRBP (3 условия) | `dim_hrbp_scope` |
| `tmp_hrbp_visible_units` | **HRBP → видимые юниты** + роль + вложенность | `dim_hrbp_scope` |
| `tmp_hrbp_viewers` | **HRBP → кто его видит** + флаг подчинения | *(не материализуется, см. § 5)* |

### Детект супер-HRBP (`tmp_super_hrbp`) — три условия

1. **Является HRBP** — есть строка в `tmp_hrbp_roots`;
2. **над ним нет HRBP** — в `tmp_head_chain` у его руководителей нет других HRBP;
3. **сидит в целевом юните** — `management_unit_rk = '50eb70d6df69372ceb7f354df8e8aa53'`.

> ⚠️ **Целевой юнит зашит в коде** (и в хелике, и в `01_dim_unit.sql`). Это
> единственное «магическое» значение ролевой модели — вынести в параметр /
> справочник и сверить с фактическим юнитом компании (см. § 6).

### Видимость (`tmp_hrbp_visible_units`)

- **Обычная зона** (`спец роль`): все листья-юниты под корнем HRBP, уровень
  которых ≥ уровня корня. Вложенность `unit_level = visible_unit_lvl - root_lvl + 1`.
- **Супер-HRBP** (`лид эйчар`): корень = уровень-2 ветки юнита (или сам юнит для
  lvl1), видит **весь** справочник юнитов.

`access_role` берётся из `MAX(is_regular_flg)`: есть хоть одна регулярная
(назначенная) зона → `спец роль`, иначе → `лид эйчар`.

## 3. Материализация в витрину: `dim_hrbp_scope`

GP (`01_dim_unit.sql`) → CH (`10_ddl.sql`):

| GP-колонка | CH-колонка | Источник |
|---|---|---|
| `hrbp_id` (`hrbp_mdm_employee_rk`) | `hrbp_id` | `tmp_hrbp_roots` |
| `hrbp_login` (`hrbp_ad_login`) | `hrbp_login` | `tmp_hrbp_roots` |
| — | `hrbp_name` | `hrbp_full_nm` / `hrbp_last_nm`+`hrbp_first_nm` *(уточнить)* |
| `access_role` | `hrbp_role` | `tmp_hrbp_visible_units.access_role` |
| `unit_id` (`visible_unit_rk`) | `unit_id` | `tmp_hrbp_visible_units` |
| `zone_root_unit_id` (`root_unit_rk`) | `zone_root_unit_id` | `tmp_hrbp_visible_units` |
| `unit_level` (вложенность) | — (в CH нет) | `tmp_hrbp_visible_units` |

`dim_unit_owner` — ответственный HRBP за узел (самая глубокая зона, регулярная
предпочтительнее супер-видимости). Из него `mart_hub` берёт
`scope_hrbp_id` / `scope_hrbp_zone_root_id` для каждой строки `scope_unit_id`:
это атрибут юнита отчёта, а не сам доступ.

## 4. Как метрики связываются с доступом (RLS)

1. **Витрина `hub_fact`** считает метрики на всех юнитах; каждая строка несёт
   `scope_unit_id` (юнит отчёта) и `scope_hrbp_id` / `scope_hrbp_zone_root_id`.
2. **Справочник доступа** `dim_hrbp_scope` — единственное место, где
   `hrbp_login` привязан к видимым `unit_id`.
3. **RLS в Superset** (dataset-spec § 10):

```sql
scope_unit_id in (
    select unit_id
    from hrbp.dim_hrbp_scope
    where hrbp_login = '{{ current_username() }}'
)
```

- У `спец роль` в `dim_hrbp_scope` лежит поддерево его корня → RLS отдаёт только
  его ветку (и всё, что под ней).
- У `лид эйчар` в `dim_hrbp_scope` лежат **все** `unit_id` (cross join по
  справочнику юнитов) → RLS отдаёт всю компанию. Роль отдельно проверять не нужно.
- **Юнит по умолчанию** на полке (корень компании) виден не всем. Для обычного
  HRBP полка должна открываться на его корне зоны: подставлять
  `min(zone_root_unit_id)` его зоны, а не глобальный корень.

> Граница ответственности: метрики считаются один раз, RLS **не пересчитывает**
> их — он лишь ограничивает, какие строки `scope_unit_id` дойдут до пользователя.

## 5. Флаг подчинения и супер-видимость (`tmp_hrbp_viewers`)

Второй выход хелика — `tmp_hrbp_viewers`: для каждого HRBP список других HRBP,
**которые видят его зону**, с флагом `is_subordinate_flg` (есть ли над ним
руководитель из `tmp_head_chain`) и ролью (`По спец роль` / `Лид HRBP`).

- Назначение — «кто меня видит», иерархия ответственности, делегирование.
- Для **RLS на метриках не нужен**: RLS строится на `visible_units`
  (`dim_hrbp_scope`), и супер-видимость уже покрыта тем, что у `лид эйчар`
  в справочнике все юниты.
- В март **не материализуется** (`01_dim_unit.sql` его не строит). Решить, нужен
  ли он фронту — например, для списка «мои HRBP», отображения зон вышестоящих
  или пометки «чья зона». Пока макет этого не требует — держим вне контура.

## 6. Настройка и подводные камни

1. **Целевой юнит супер-HRBP зашит** (`'50eb70d6df69372ceb7f354df8e8aa53'`)
   и в хелике, и в `01_dim_unit.sql`. Вынести в параметр/справочник, сверить
   значение с фактическим юнитом компании.
2. **`hrbp_name` в CH** нечем заполнять из текущего `01_dim_unit.sql` — взять
   из базы (`hrbp_full_nm` / `hrbp_last_nm`+`hrbp_first_nm`).
3. **Маппинг роли на `hrbp_role`.** В GP роли русские (`спец роль` / `лид
   эйчар`); договориться о кодировке в CH (латиница: `assigned` / `super`) —
   чтобы не тащить кириллицу в LowCardinality-ключ.
4. **`hrbp_login` совпадает с AD-логином в Proteus** — иначе `current_username()`
   ничего не отдаст. Логин протянут на всю историю («последнее известное
   значение») — при исторических срезах может не соответствовать факту на дату.
5. **Реорганизации.** Зоны пересобираются из среза `last_day_flg = 1`; прошлые
   периоды в отчёте под новую структуру не пересматриваются — как и у метрик.
6. **`is_subordinate_flg` строится по цепочке руководителей**
   (`tmp_head_chain` / `lvl*_management_head_*`), а не по `subordination_lvl`
   (этого поля в базе нет). `subordination_lvl` для ролевой модели не требуется.
